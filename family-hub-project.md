## Key context (read this first in any new chat)

- **Project:** A wall-mounted family command center running on a tablet or touchscreen + Raspberry Pi
- **Owner:** Trey — Westminster, CO. Basic coding background (scientist-level scripting, not software dev). Has built simple apps with Claude before.
- **Family:** Trey + wife Beryl (iPhone), kids Bryce and Emery
- **Ecosystem:** Primarily Google (Gmail, Google Calendar, Google Tasks). Beryl on iPhone — must work cross-platform. Google Keep is **not used** — its API is Workspace-only and unavailable on personal Gmail accounts (confirmed 2026-08-05); groceries and any Keep-style lists live in Google Tasks instead (separate task lists, same OAuth).
- **Stack decision:** Custom React app (not Home Assistant dashboard) hosted on GitHub Pages (free). Home Assistant may be added later as a hybrid backend for smart home control — designed to be addable without breaking existing code.
- **Cost constraint:** No ongoing subscription costs. Upfront hardware/one-time costs OK.
- **Google API note:** OAuth setup is the trickiest one-time step. Once done, all subsequent Google APIs reuse the same auth.
- **Display aspect ratio:** 16:9 landscape (most common wall-mount orientation). Locked via CSS padding-top trick. Easy to change. All sizing in `em` units so it scales to any screen size.
- **AI agent:** simpsonfamilyhubapp@gmail.com, watched by a Google Apps Script (`apps-script/family-agent.gs`) that parses emails with Gemini and writes to Google Tasks/Calendar. Live and tested (T-09) — voice-dictate via Siri/Gemini to that address to add tasks, calendar events, or multi-item grocery lists hands-free.
- **App structure principle:** Modular panel/nav architecture — every feature is its own component behind a nav item. Makes adding new features (smart home, budget, etc.) trivial without touching existing code.
- **Current state:** Live React app, not the old single-HTML mockup — see "Current architecture" below for the real file layout.
- **Tooling:** Phase 3 onward should use Claude Code (CLI) for file editing + GitHub for version control and cross-machine sync.

## Resume on a new machine

Everything is committed and pushed to GitHub — nothing lives only on one PC. To pick this project back up anywhere:

1. **Install prerequisites** (if not already on the machine): [Node.js LTS](https://nodejs.org) and [GitHub CLI](https://cli.github.com). On Windows, `winget install OpenJS.NodeJS.LTS` and `winget install GitHub.cli` both work well via Claude Code's Bash/PowerShell tool.
2. **Clone the repo**: `git clone https://github.com/treysimpson/family-hub.git` (repo is public, so no auth needed just to clone — but `gh auth login` is needed for pushing later; walks through a one-time-code browser flow).
3. **Install deps**: `cd family-hub && npm install`.
4. **Open Claude Code in that folder** and paste this whole file into the chat (or just say "read family-hub-project.md and continue") — that's the standing instruction at the top of this doc, and it gives a fresh Claude session everything it needs.
5. **`npm run dev`** starts the app at `http://localhost:5183/family-hub/` (port is pinned in `vite.config.js` — this exact origin is authorized in the OAuth client; don't change it without also adding the new one in Google Cloud Console → APIs & Services → Credentials → "Family Hub Web Client"). Sign-in, Calendar, Tasks, Groceries, and the email agent are all live and tested (T-01–T-09 done, see To-do list below) — the remaining work is whatever Future backlog item (T-10+) gets prioritized next. The Chores rebuild (custom localStorage-based recurrence) is **built as of 2026-10-26** — see T-36 below; the points-*value*/reward side of it is still an open design question, not built.
6. If anything errors, check the browser console — `AppContext.jsx`'s `calendarError`/`tasksError` state and `googleAuth.js`'s `authError` are surfaced but not yet shown anywhere in the UI beyond the Settings panel's sign-in button, so console logs are the fastest way to see what broke.

**Nothing is machine-specific** — no local-only config, no secrets in untracked files, no machine-specific paths in the codebase. The OAuth client ID is public-safe and lives directly in `src/lib/googleAuth.js`. One exception: the Budget PIN lives in browser `localStorage`, not the sheet — a different browser/machine won't have it and will prompt to set a new one the first time Budget is opened there, which is expected, not a bug.

## Current architecture (as of 2026-08-06)

The React app lives at the repo root (not in a subfolder). Key files for a fresh session to know about:

- **`src/lib/googleAuth.js`** — Google Identity Services (GIS) browser token flow. No backend, no client secret used. Exports `signIn()`, `signOut()`, `trySilentSignIn()`, `getStoredToken()`. Token is cached in `sessionStorage` (clears on tab close, which is fine/expected).
- **`src/context/AuthContext.jsx`** — wraps the above in React state (`isSignedIn`, `accessToken`, `signIn`, `signOut`, `signingIn`, `authError`). Auto-schedules silent token refresh 5 min before expiry. Wraps the whole app in `App.jsx`, outside `AppProvider` (Auth has to exist first since `AppContext` reads from it).
- **`src/lib/googleCalendar.js`** — `fetchEvents(accessToken, timeMin, timeMax)`, normalizes raw Calendar API events into `{id, title, allDay, start, end, location, notes, who, color}`.
- **`src/lib/googleTasks.js`** — full Tasks API wrapper: `ensureTaskLists` (auto-creates named lists), `fetchTasks` (deliberately omits `showHidden` — see comment in the file), `insertTask`, `setTaskStatus`, `deleteTask`, `clearCompletedTasks`, `pruneStaleCompleted` (permanently deletes completed items older than 3 days so lists do not grow unbounded). `PERSON_LISTS` and `STORE_LISTS` constants define the 7 list names.
- **`src/lib/dateGrid.js`** + **`src/lib/buildCalendarViews.js`** — pure date-math + transform functions that turn a flat list of Calendar events into the exact month-grid/week-days/agenda-groups shapes the view components expect. No date library dependency.
- **`src/context/AppContext.jsx`** — the hub. Fetches weather (always), calendar events + tasks (only when `isSignedIn`). Tasks poll every 30s (`TASKS_REFRESH_MS`) via a ref (not the `taskListIds` state) to avoid a stale-closure bug in the interval; Tasks/Groceries pages also call `refetchTasks()` on mount so opening the tab always shows the latest data immediately. Exposes `calendarViews` (either live-built or the original mock data, picked automatically) and `tasksLive`/`personTasks`/`groceryTasks` + action functions. **Every page component branches on `tasksLive`/`calendarViews.live`** to decide whether to render real data or fall back to `src/data/mockData.js` — so the app is always fully functional and demo-able even signed out.
- **`src/lib/weather.js`** — Open-Meteo fetch + normalize, no auth needed, independent of Google sign-in.
- **`src/data/mockData.js`** — still used for family member info (names/colors), chores, home control, and as the signed-out fallback for calendar/tasks. Weather mock data was removed (T-05) since weather has no signed-out/signed-in distinction — it's just always live.
- **`apps-script/family-agent.gs`** + **`apps-script/README.md`** — the T-09 email AI agent's source, kept in the repo for version control only (Apps Script doesn't deploy from GitHub; changes must be manually re-pasted into script.google.com). Runs under Trey's own Google account, not simpsonfamilyhubapp@gmail.com, since Google Tasks lists can't be shared cross-account. Nine polling functions, each on its own 5-minute trigger except the monthly allowance one: `processFamilyAgentEmails` (T-09), `processBudgetEmails`, `processAmazonOrderEmails`, `processTargetOrderEmails`, `processTargetReceiptImports`, `processCostcoReceiptImports`, `processStatementImports` (T-11), `processWorkExpenseImport` (added 2026-08-22, see below), `addMonthlyFunMoneyAllowance` (day-1-of-month trigger). Also has `lookupMerchantMemory_`, consulted by both `processBudgetEmails` and `processStatementImports` before trusting Gemini's category guess — reads the "Merchant Memory" tab, which the React app (not this script) writes to when a transaction gets manually recategorized and "Always" is chosen (T-11 Phase D). `lookupMerchantName_` runs right after (still keyed on the original raw merchant text, so a rename never affects its own category-memory entry) and reads the "Merchant Names" tab, written when a merchant gets renamed — replaces cryptic raw merchant text (e.g. "SONDERMIND INC") with a readable name (e.g. "Beryl's Therapy") on every future transaction from that source. Don't rename "Amazon.com" this way — `applyAmazonOrder_` matches on "amazon" appearing in the merchant text. **Automatic receipt routing (added 2026-08-09)**: `processFamilyAgentEmails` now checks any image attachment on a Family Agent email with `routeReceiptImage_`/`classifyReceiptImageWithGemini_` — a cheap Gemini image classification pass separate from the detailed Target-specific extraction — before trying to parse it as a task/event/grocery request. A recognized Target receipt gets moved straight to the `Target Receipt` label (no manual labeling, and it works for Beryl too, since it goes through the shared simpsonfamilyhubapp@gmail.com address rather than a self-addressed email that only Trey could send). A recognized Costco receipt is parked under a new `Costco Receipt` label, processed by `processCostcoReceiptImports` (built 2026-08-10, see below). Anything else falls through to the normal parse/Needs Review as before.
  - **Budget core** (`processBudgetEmails`) — parses Chase/Amex transaction-alert emails (labeled "Budget Agent," arriving directly in Trey's inbox, no forwarding needed) into a "Transactions" tab of an auto-created "Family Hub Budget" Google Sheet. Live and tested 2026-08-06. Categories (Trey's real household list): groceries, dining, gas-auto, travel, household, entertainment, healthcare, kids-activities, kids-other, bills-utilities, beryl-personal, trey-personal, shopping, trey-work, plus structural one-time (major/non-recurring) and other (fallback) — one-time and trey-work (reimbursable) are excluded from the regular monthly total and shown as separate lines (`EXCLUDED_FROM_BUDGET`). `setupBudgetSheets` (run manually once) creates three more tabs: **Budget Targets** (category → monthly target, populated with real categories, defaults 0), **Fixed Bills** (recurring-bill merchant names, not yet populated), **Fun Money** (see below).
  - **Fun money** (Phase C, live and tested 2026-08-06) — `fun_spend`/`fun_return` actions on `processFamilyAgentEmails` (message-driven, not card-alert-driven, so it's on the family-request pipeline not the budget one). Ledger-style: balance per person = sum of their rows, so rollover needs no extra logic. `addMonthlyFunMoneyAllowance` deposits $250 into each of Trey's and Beryl's pools on a monthly trigger — amount set in `FUN_MONEY_MONTHLY_AMOUNT`.
  - **Amazon itemization** (`processAmazonOrderEmails`, deployed and tested 2026-08-06) — Amazon's order-status emails only give item counts per coarse category, not per-item prices (no automatable/ToS-safe way to get real line-item pricing exists — Amazon has no order-history API and scraping risks account flags), so it tags the whole order with its majority category and updates the matching Transactions row in place (by amount match), never creating a new row. Handles multiple orders per email. Beryl's orders need her own sender-specific forwarding setup since they land in her inbox, not Trey's (not routed through simpsonfamilyhubapp@gmail.com, to avoid Amazon receipts getting mislabeled as family requests) — see `apps-script/README.md`. Caught and fixed a real bug during testing: `orders.every(applyAmazonOrder_)` short-circuited on the first unmatched order in a multi-order email, silently skipping every order after it (including ones that would have matched), since `.every()` stops calling its callback once it hits a false — switched to `.map()` + a separate `.every(Boolean)` check.
  - **Target order & receipt itemization** (`processTargetOrderEmails`, `processTargetReceiptImports`, Phase E, added 2026-08-07, not yet tested) — unlike Amazon, both Target.com order confirmations and the Target app's in-store Purchase History screen show real per-item prices, so these genuinely split a charge across categories instead of tagging it with one majority guess: the matching Transactions row (already created by `processBudgetEmails`) is deleted and replaced with one row per category via `splitTransactionRow_`, each holding that category's proportional share of the total (tax/shipping prorated by subtotal share via `computeCategorySplit_`), so a plain SUM still nets to the same charge. `processTargetOrderEmails` mirrors the Amazon pipeline (Gmail filter + label, matches within `TARGET_ORDER_MATCH_TOLERANCE` = $5 of amount rather than exact — found during live testing that an order confirmation total can differ from the real charge, e.g. a quoted bag fee that was not actually charged — taking whichever unclaimed Target row is closest, and splitting against that row's real charged amount rather than the email's total so the discrepancy is absorbed instead of blocking the match; same Beryl-forwarding setup). `processTargetReceiptImports` is manual, like statement import: Target does not email a receipt for in-store purchases, so a screenshot of the itemized purchase-detail screen (or a photo of a paper receipt) is emailed in and parsed with Gemini's native image understanding — same capability `processStatementImports` uses for PDFs, just a different mime type. If a card-alert row already exists for that date/amount it gets replaced with the split (`findTransactionRow_`); if not, the split is appended as new rows, filling the gap the way statement import does. **Item detail (added 2026-08-08, per Trey's request "moving forward anytime that info is available then use it")**: since Gemini already sees real item names when itemizing Target orders/receipts, `appendOrderItems_` now writes them to a new **Order Items** tab (EmailId, Item, Category) instead of throwing them away once the category subtotal is computed — keyed on EmailId rather than order number so it works uniformly for both orders and receipts (receipts have no order number). `processTargetOrderEmails` only records items for orders that actually matched on a given run (an unmatched order retries with a fresh Gemini parse next run, so recording eagerly would duplicate items once it does match). Amazon itemization and statement import never write here — neither pipeline gets real per-item names from Gemini. `appendOrderItems_` is idempotent (skips an email that already has rows), so it is safe to call more than once for the same email. `backfillTargetOrderItems`/`backfillTargetReceiptItems` (added 2026-08-09) handle orders/receipts that were already moved to `.../Done` before the Order Items tab existed — a normal re-run only looks at the still-unprocessed label and would not touch them, and by that point the Transactions row is already split so re-matching would not work anyway; these instead read the `.../Done` label directly, re-parse with Gemini, and record item names only, without touching Transactions. **Fixed 2026-08-09** (caught via live testing — Details never showed up despite Order Items having rows): `splitTransactionRow_` was carrying forward the EmailId of the *original* row it replaced, which belongs to the bank's card-alert email, not the Target order/receipt email `appendOrderItems_` actually keyed its rows on — so the two could never match. `splitTransactionRow_` now takes `emailId` as an explicit parameter (the order/receipt email's own ID) instead of reading it off the old row, threaded through from `applyTargetOrder_`/`processTargetReceiptImports`. This only fixes future runs; the two already-mismatched test rows needed a manual EmailId correction directly in the sheet.
  - **Statement import/reconciliation** (`processStatementImports`, Phase E, added 2026-08-06, not yet tested against a real statement) — Gemini has native PDF document understanding, so the statement PDF is sent directly as `inline_data` with no OCR step. Extracts every purchase/refund line item (explicitly excludes payment/balance-transfer lines, which aren't purchases), skips anything already in Transactions (matched by date + amount, since a statement's merchant text often differs from the live alert's), appends the rest as new rows tagged "Statement import" in Notes. Same function serves both the one-time historical backfill and ongoing monthly reconciliation. Manual/infrequent, so no auto-forward or filter — just email yourself the downloaded PDF with the label `Statement Import` applied. Known gaps: de-dupes on date+amount only (no stronger identifier available), and only reads the first PDF attachment per email.
  - **Manual recategorize / merchant memory / merchant rename** (Phase D, added 2026-08-06, not yet tested) — the React app writes directly to the sheet for this one (see below), not the Apps Script; `setupBudgetSheets` now creates a fourth and fifth tab, **Merchant Memory** (Merchant/Category, empty until a correction happens) and **Merchant Names** (Raw Merchant/Display Name, empty until a rename happens), which `lookupMerchantMemory_`/`lookupMerchantName_` consult before trusting Gemini in both `processBudgetEmails` and `processStatementImports`. Recategorizing now prompts "Just this once" vs. "Always for [merchant]" (only "Always" writes Merchant Memory) since merchants like Target legitimately span multiple categories and a blanket rule from one correction is often wrong; renaming always remembers (no "just this once"), since a cryptic raw merchant string is essentially always worth translating permanently.
  - **Work expense import / auto-tag as trey-work** (added 2026-08-22, built but not yet live-tested — script not yet re-pasted into script.google.com) — Trey's employer reimburses work expenses through Payhawk; he pays on his own personal card first (the same cards this whole Budget system tracks), so a Payhawk export can be cross-referenced against Transactions to auto-tag the matching row `trey-work` instead of him doing it by hand. `processWorkExpenseImport` reads a Payhawk CSV export (emailed in, labeled `Work Expense Import`, same manual/infrequent pattern as Statement Import) into a new **Work Expenses** tab (Expense ID/Date/Amount/Currency/Category/Note/Matched) — parsed directly by Payhawk's known column headers (`parsePayhawkCsv_`, via `Utilities.parseCsv` so embedded commas in the Expense Note column don't break it), not through Gemini, since the header set is small and fixed. `matchWorkExpenses_` then matches each unmatched Work Expenses row to a Transactions row by date (±3 days) + amount (exact for USD, $5 tolerance for anything Payhawk converted from another currency, since its own FX conversion won't necessarily equal what the card network actually charged) — a match sets category to `trey-work` and tags Notes `Work expense #<id>`, guarding against ever double-claiming the same row. Runs automatically after every `processWorkExpenseImport`, `processBudgetEmails`, and `processStatementImports` pass (only when something new was actually added), plus a manual `matchWorkExpensesNow` for an on-demand re-run. Investigated against a real Payhawk export (356 line items, Feb 2024–Sep 2026, LUMICKS) before building this: confirmed its `Supplier Name` column is *not* a real merchant name for personal-funds reimbursements (it's the employee's own name), so date+amount is the whole matching key — no merchant cross-check available, which is the main known false-match risk (see apps-script/README.md's Known Limitations).
- **`src/lib/googleSheets.js`** — Sheets API wrapper, now read/write (not read-only, as of Phase D 2026-08-06 — see `googleAuth.js` scope note below). Reads: `fetchTransactions` (each row includes its 1-indexed sheet `row` number so writes can target it directly), `fetchBudgetTargets`, `fetchFixedBills`, `fetchFunMoney`, `fetchOrderItems` (added 2026-08-08, reads the new Order Items tab; the latter four fail soft to empty rather than erroring, since those tabs may not exist yet, or a given transaction may just have no item detail at all — Amazon/statement-import rows never will). Writes: `updateTransactionCategory(accessToken, row, category)`, `updateTransactionMerchant(accessToken, row, merchant)`, `upsertMerchantMemory(accessToken, merchant, category)`, `upsertMerchantName(accessToken, merchant, displayName)` (the two upserts share a common `upsertKeyValue_` helper — updates the existing row for that key if found, else appends). Also exports `TRANSACTION_CATEGORIES`, mirrored from the Apps Script's list, for the recategorize dropdown. `BUDGET_SPREADSHEET_ID` is set to the real "Family Hub Budget" spreadsheet ID. Has a `normalizeDate` helper because Sheets silently auto-converts date-shaped strings to its own date type even when written via `appendRow`, so date cells can come back as a raw serial number instead of the "YYYY-MM-DD" string that was written — worth remembering for any future column that looks like a date.
- **`src/lib/googleAuth.js`** — `SCOPES` upgraded 2026-08-06 from `spreadsheets.readonly` to full `spreadsheets` for Phase D writes. The matching Cloud Console step (Data Access → Add or remove scopes → Google Sheets API → `.../auth/spreadsheets`) is done — confirmed 2026-08-17 that both the readonly and full scopes are checked.
- **`src/context/AppContext.jsx`** — `selectedBudgetMonth`/`setSelectedBudgetMonth` (added 2026-08-07, a "YYYY-MM" string, defaults to the real current calendar month) now drives every Budget total (`budgetMonthTotal`, `budgetCategoryTotals`, `budgetOneTimeTotal`, `budgetReimbursableTotal`, `budgetFixedTotal`, `budgetDiscretionaryTotal`, and the raw `selectedMonthTransactions` list) — these were already calendar-month-boundary math (`t.date.startsWith(monthPrefix)`, not a rolling N-day window), but were previously locked to whatever `new Date()` returned with no way to look at a past month; making the month an explicit, navigable piece of state is what actually fixes that. Fun Money intentionally is NOT scoped to this — it stays its own ledger-style running total regardless of which month is selected. `recategorizeTransaction(transaction, category, remember = true)` (added 2026-08-06): optimistically updates local state, then calls `updateTransactionCategory`; rolls the optimistic update back and sets `budgetActionError` if that write fails (self-reviewed catch before this was ever live-tested — an unrolled-back optimistic update would have shown a category as saved when it was not, e.g. during tonight's own window before the OAuth scope is upgraded). `upsertMerchantMemory` is separately best-effort (logged, not surfaced) since the category change is the part that matters to the user, and is skipped entirely when `remember` is false (the "just this once" choice). `renameMerchant(transaction, displayName)` (fixed 2026-08-08 — originally only renamed the single tapped row) now finds every existing transaction sharing the same raw merchant text and renames all of them, not just the one tapped: optimistically updates all matching rows, writes each via `updateTransactionMerchant` with `Promise.allSettled`, and rolls back only the rows whose write actually failed (not the whole batch) before best-effort `upsertMerchantName` for future transactions.
- **`src/components/PinGate.jsx`** — client-side-only PIN gate (localStorage, not real security — good enough to stop casual viewing on the shared wall display, not a determined attacker) used by `BudgetPage.jsx`. Reset via Settings panel ("Forgot PIN").
- **`src/pages/BudgetPage.jsx`** — a `‹ Month Year ›` nav row (added 2026-08-07, next-month arrow hidden once you're back at the real current month — can't navigate into the future) sits above the total-spend card and drives `selectedBudgetMonth`, so every sidebar stat and the whole transactions list below reflect whichever month is selected, not just "now": total monthly spend across all cards (tap to drill into a per-category breakdown, with over/under shown once a category has a non-zero target), a "Major expenses this month" line for the one-time bucket, a "Trey's work (pending reimbursement)" line, a fixed-vs-discretionary split (once Fixed Bills has entries), Fun Money balance cards for Trey/Beryl (not scoped to the selected month — ledger-style running total — red/coral styling when a balance drops below `FUN_MONEY_LOW_THRESHOLD`, currently a flat $25) with a recent-spends list, and a "{Month Year} transactions" list showing *every* transaction in the selected month (not a fixed recent-10 — this is the "click a month, see all its details" view) where tapping a transaction's category opens an inline dropdown, then a "Just this once" / "Always for [merchant]" choice before actually saving (added 2026-08-06), and tapping the merchant name itself turns it into a text box to rename it (also added 2026-08-06) — both blocked on the OAuth scope step above until they can actually write. A row also shows a "Details" toggle (added 2026-08-08, via `orderItemsByEmailId` from AppContext; **filtered to that row's own category as of 2026-08-09** — a source email's item list spans every category the order got split into, so without filtering the Household row would also show the Kids Other items) whenever it has item-level data for its own category — expands to just that row's item names, no prices shown per Trey's request. Only Target order/receipt transactions ever have this; Amazon and statement-import rows never show a Details control since neither pipeline captures real item names — all gated by `PinGate`. Sign-in check uses `useAuth()` directly (not `useApp()`, which doesn't re-expose `isSignedIn` — caused a real bug where the page always showed "not signed in" regardless of actual state, fixed 2026-08-06).

**Design pattern to preserve going forward:** any new Google-backed feature should follow the same shape — a thin `src/lib/googleX.js` REST wrapper, state + derived view in `AppContext`, and the consuming page component branching on a `live` flag with a mock fallback. This keeps the app safely demoable at every commit and matches how Calendar/Tasks were done.

## Things to never forget

- **Module/panel architecture from day 1** — every feature is its own React component behind a nav item. Never build monolithic pages.
- **Google Home API is restricted** — no public API for device control. Must go through Home Assistant (Phase 4). Don't try to call Google Home directly from React.
- **Beryl is on iPhone** — any sync mechanism must work natively on iOS. Google Tasks + Calendar both have good iOS apps. Avoid Android-only solutions.
- **GitHub Pages is the deploy target** — static hosting, free. React app must be a static build (no Node server at runtime). Vite handles this cleanly.
- **Google Apps Script agent is serverless** — runs on Google's infrastructure. Pi not required for the agent.
- **Google Keep has no API for personal accounts** — Keep API is Workspace-only (admin-approved business accounts). Dropped from the plan 2026-08-05; everything Keep would've done lives in Google Tasks instead.
- **One Google OAuth setup covers Calendar + Tasks** — same credentials, no Keep scope needed.
- **OAuth requires a real URL** — set up GitHub Pages deploy before configuring Google Cloud OAuth consent screen.
- **OAuth app stays in "Testing" mode** — External audience, only the 2 test users (Trey + Beryl) can authorize it; no Google app verification needed since it never goes to Production. If either sign-in ever fails with an "app not verified" or "access blocked" error, check that their email is still listed under Audience → Test users in the Google Auth Platform console.
- **Beryl must complete her own Google sign-in/consent** the first time she uses the app on her device — Trey authorizing doesn't cover her account.
- **Use Claude Code for Phase 3** — much better than chat for file editing, running commands, and iterating on a real codebase. Use GitHub to sync across machines.
- **Dark theme contrast** — defer readability tuning until app is on the actual wall display. Hardware + ambient light affects this significantly.
- **Open-Meteo for weather** — free, no API key, no auth. Just lat/long. Perfect for this use case.

## Lint/bug pass (2026-10-26)

Ran `npm run lint` (`oxlint`) for the first time this session — hadn't been run against the day's additions. Found and fixed two real bugs, beyond pure style warnings:
- **`src/lib/googleAuth.js`**: `requestToken`'s `new Promise(async (resolve, reject) => ...)` meant a rejection from `getTokenClient()` (e.g. the Google Identity Services script failing to load — blocked by an ad blocker, no network) had nowhere to go; an async Promise executor's own rejection doesn't call the outer `reject`. The returned promise would just hang forever, so `signIn()` would sit on "Signing in…" indefinitely with no error ever shown. Rewritten without an async executor, chaining `.then()/.catch(reject)` instead — a real rejection now correctly reaches `AuthContext.jsx`'s `catch` and surfaces as `authError`.
- **`src/lib/buildCalendarViews.js`**: `buildAgendaGroups` took a `days = 14` parameter that was never actually applied anywhere in the function body — every future calendar event showed up in the Agenda tab with no upper bound at all, not just the next 2 weeks as the parameter implied. A single far-out event (a yearly recurring one, a vacation booked a year ahead) would sit at the bottom of Agenda indefinitely. Fixed to filter against a real `today + days` horizon; verified with a standalone Node sanity check (events at +1/+13/+15/+365 days — only the first two now included).
- Also cleaned up two pure style warnings (a ternary used only for its side effect in `CalendarPage.jsx`, an async executor's unused-parameter double of the same googleAuth.js fix). Remaining 4 lint warnings are all `react(only-export-components)` fast-refresh notices on pre-existing files that intentionally export both a component and shared helpers/constants — cosmetic, not bugs, left alone.
